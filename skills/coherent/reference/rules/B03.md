# B03 — Premature abstraction

Investigation procedure only. Catalog metadata lives in
[taxonomy.md](../taxonomy.md). Detection: hybrid. Detector emits
`single-impl:<Name>` for interfaces/abstract classes with one production
implementation. Record: `decisions.json`. Shared write-back: [README.md](README.md).

## What to search for

Mechanical: one impl. Also look for factories and shared helpers introduced
before a second real call site existed.

Names matching `Repository|Store|Client|Gateway|Port|Adapter` are reported
at lower confidence — a single adapter can still be a real I/O boundary.

## Distinguish a real issue from an intentional difference

- Intentional: a persistence or provider port with one adapter today and a
  declared external boundary.
- Intentional: a test double does not count as a second production impl
  (the detector ignores test files).
- Real: the abstraction freezes an incomplete understanding; the obvious
  code is harder to change than the rare variant that never arrived.
- Not B03: a generic registry with one member (B02); a forwarding wrapper
  (B04).

## Evidence to collect

- Abstraction, sole impl, and every call site.
- Whether architecture names this as a boundary.
- `deletionOpportunity`: collapse interface + impl into one type.

## Successful “do not merge”

`PaymentClient` (port) and `StripePaymentClient` (adapter) stay distinct
because Stripe is an external boundary. Dismiss `single-impl:PaymentClient`.

## How to write the result

Confirm in `decisions.json` when no second impl is planned and no boundary
justifies the split. Dismiss at I/O/provider edges.
