# E03 — Over-fetching

Investigation procedure only. Catalog metadata lives in
[taxonomy.md](../taxonomy.md). Detection: hybrid. No detector ships yet.
Ordinary reviews follow [data-access.md](../data-access.md) and report in chat.
Explicit advanced cleanup uses `decisions.json`; shared write-back:
[README.md](README.md). Prerequisite judgment: A06 (which representation is
authoritative).

## What to search for

Queries, API calls, or aggregates that load a wide payload when the caller
uses a narrow projection: `SELECT *`, `include: { everything: true }`,
fetch-then-pick-two-fields.
Also inspect entire collections fetched only for counts or existence, detail
loaded for inactive consumers, duplicate client/server requests, polling with
no consumer, and refetch triggers without a freshness requirement.
Trace superseded requests after search/filter changes, navigation or tenant
switches, and full-scope refreshes after each item in a batch. Check consumers
of success, error and loading state, not just the fetched payload.

## Distinguish a real issue from an intentional difference

- Intentional: a public API that must return the wide contract.
- Intentional: an aggregate loaded once for many consumers in the same
  request (maybe E01 if it is loaded many times).
- Intentional: prefetch with a concrete latency benefit or refresh required
  after a mutation; trace those consumers before removing it.
- Intentional: in-flight work still serves another active consumer or required
  synchronization. An abandoned screen does not make every operation obsolete.
- Real: an obsolete read continues without a consumer, or its late completion
  replaces current data/errors or clears a newer request's loading state.
- Real: every batch item invalidates/refetches a whole collection even though
  one refresh at a recoverable batch boundary meets the freshness contract.
- Real: consumers couple to unused fields; later representation cleanup
  gets harder.

## Evidence to collect

- Query/call, fields loaded, fields read.
- Whether A06 already named a narrower representation.
- Trigger, active consumers, invalidation and freshness requirements; compare
  requests before and after activation, reopening and mutation.
- Whether an aggregate/projection or demand-triggered load preserves access,
  errors and completeness. Do not load all rows just to calculate locally.
- Request identity/scope, cancellation support and completion/finalization
  guards. Exercise out-of-order successes and errors and scope changes.
- Refresh counts at representative batch sizes, required intermediate
  visibility, mutation invalidation and recovery after partial completion.

Cancel obsolete reads where supported and guard application of their results.
Cancellation does not prove that server work or an external write stopped;
preserve authoritative read-back and uncertain-outcome recovery. Use E06 for
missing collection/concurrency bounds and E02 for repeated rebuild work; avoid
duplicate findings for one cause.

## Successful “do not merge”

A list endpoint and a detail endpoint that share a type but different
projections. Keep both contracts; do not force one payload.

## How to write the result

Report excess data or unnecessary load triggers with exact consumers and
contract evidence. For explicit advanced cleanup, append a hybrid finding with
`identity`: `overfetch:<file>:<fn-or-query>`; no mechanical E03 detector ships.
