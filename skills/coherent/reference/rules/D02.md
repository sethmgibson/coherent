# D02 — Defensive programming

Investigation procedure only. Catalog metadata lives in
[taxonomy.md](../taxonomy.md). Detection: hybrid. No detector ships yet.
Record: `decisions.json` until a candidate exists, then
`decisions.json`. Shared write-back: [README.md](README.md). Judge C01 first:
if the invariant is missing at the source, that is the finding.

## What to search for

Null checks, retries, and fallbacks sprinkled at every layer of an
already-owned contract. `value ?? default`, empty catch + retry, “just in
case” optional chaining through trusted internals.

Ask which violated invariant makes the fallback necessary.

## Distinguish a real issue from an intentional difference

- Intentional: a single check at the untrusted boundary (HTTP, queue) that
  owns the contract.
- Real: every layer re-checks; the real failure mode is invisible.
- Not D02: swallowed errors that drop the failure (D03); patches that exist
  because the source type is wrong (C01).

## Evidence to collect

- Each defensive site and the contract it is trying to enforce.
- The boundary that already owns (or should own) that contract.
- A fallback that hides a bug you can still trigger.

## Successful “do not merge”

A parse at the CLI boundary and a `?? []` inside a trusted helper look
similar. The CLI parse stays; the inner fallback is the issue. Do not
collapse them into one “remove all checks” finding.

## How to write the result

Append `identity`: `defensive:<symbol-or-layer>` or review a mechanical
candidate. Confirm when defense does not own the invariant.
