# E06 — Algorithmic complexity

Investigation procedure only. Catalog metadata lives in
[taxonomy.md](../taxonomy.md). Detection: hybrid. Detector emits
`loop-find|some|every|indexOf:<file>:<fn>` and `nested-loop:<file>:<fn>`.
Ordinary reviews follow [data-access.md](../data-access.md) and report in chat.
Shared write-back for explicit advanced cleanup: [README.md](README.md). Last
on purpose: the right algorithm on the wrong architecture is wasted work.

## What to search for

Mechanical: `.find()` / `.some()` / `.every()` / `.indexOf()` inside a loop;
nested loops. Multiple sites in one function should be one finding with
occurrence evidence (do not split by line).

The detector skips directly provable small fixed array literals, reports the
collection receiver or loop iterables, and uses medium confidence because it
does not infer operational input size.

Also inspect: repeated linear scans of the same list, O(n²) pairing of
in-memory collections that are large in production.
Inspect unrestricted collection reads, page sizes, accumulated buffers and
per-item concurrency across pages/workers. Also inspect costly query shapes:
joins that multiply rows, correlated work, large scans/sorts and pagination.
The current detector establishes neither workload bounds nor database cost;
these require source/runtime and query-plan investigation.

## Distinguish a real issue from an intentional difference

- Intentional: tiny fixed sets (catalog of 30 rules, a handful of flags).
- Intentional: a nested loop whose inner bound is 1–2.
- Real: a hot path whose actual size and access pattern need a better
  structure.
- Real: growing inputs can exceed memory, connection or provider limits
  because collection size, buffering or concurrency has no effective bound.
- Intentional: an export needs every row but streams bounded pages with
  backpressure. A fixed small fan-out can also be sufficient as written.
- Intentional: a sequential database scan with an appropriate plan at the
  actual scale. Scan type or query count alone is not proof of excess cost.
- Do not overfit a micro-benchmark. The detector does not claim operational
  severity without input scale.

Duplicate fingerprints for the same `loop-find:file:fn` are one issue.

## Evidence to collect

- Function, method, occurrence count, and typical input size.
- Whether the function is already A08-dead (then this finding should
  disappear).
- A simpler structure that preserves behavior.
- Effective page/batch/concurrency limits across the whole workflow; peak
  in-flight work and retained data with representative inputs above a boundary.
  Verify stable ordering, complete results and safe retries/resumption.
- For query/index changes: actual schema, existing indexes, representative
  parameters/cardinalities and query-plan evidence. Compare rows processed and
  returned, duplicate handling and aggregate correctness, not just round trips.

Start with non-executing `EXPLAIN` or existing traces. `EXPLAIN ANALYZE` executes
the statement; use execution profiling only within the authorized environment
and side-effect boundaries. Separate estimated cost from measured execution.
Test joins with zero, one and multiple related rows. Missing plan or scale
evidence leaves a candidate; do not invent an index recommendation from syntax.

## Successful “do not merge”

Two nested loops in different functions, or a catalog scan vs a request-path
scan. Do not merge unrelated sites. Dismiss catalog-scale O(n²).

## How to write the result

Report only on a surviving path with known scale or a demonstrated missing
bound. For explicit advanced cleanup, confirm an existing finding or add an
evidence-backed hybrid finding for a missed case. Dismiss small fixed inputs
with actual bounds. If the detector emitted duplicates, review once and treat
the rest as the same identity. Keep one finding per cause when E01/E03 also
describe the same query chain.
