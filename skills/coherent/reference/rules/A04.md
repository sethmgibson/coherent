# A04 — Duplicate implementations

Investigation procedure only. Catalog metadata lives in
[taxonomy.md](../taxonomy.md). Detection: hybrid. No detector ships yet.
Record: `semantic-findings.json` until `findings.json` has a candidate, then
`reviews.json`. Shared write-back: [README.md](README.md).

## What to search for

After A01/A02 have named the living concepts, search for the same *behavior*
in more than one place.

- Two functions or classes that create, authorize, price, persist, or notify
  the same concept.
- Near-copy sequences of calls with a renamed helper.
- Comments: “copied from”, “same as X”, “temporary duplicate”.
- Tests that assert the same outcome through two production entrypoints.
- A feature module that reimplemented a path it did not find.

Inspect callers and callees of each copy. Do not flatten the tree looking for
similar shapes.

## Distinguish a real issue from an intentional difference

Same shape is not same behavior.

- Intentional: different invariants, actors, or side effects (charge a card vs
  record a ledger line).
- Intentional: a thin public facade that only forwards (that is B04, not two
  implementations).
- Real: a fix or invariant would have to land N times; the copies already
  drifted.
- Not A04: two types for the same information (A06); two named architectures
  for the same job (A05); one unused extra copy with no callers (A08).

A successful audit may conclude the copies must stay distinct.

## Evidence to collect

- Inputs, outputs, and side effects of each copy, side by side.
- Callers of each; which one new work would extend.
- `semanticEquivalence` and `authoritativeConcept` (the surviving
  implementation).
- `deletionOpportunity` for the others, including tests and helpers that
  become dead (reconsider A08, B04, B05, D04, D05 after a merge).
- Behavioral tests that already pin the surviving path.

## Successful “do not merge”

Two authorize functions look alike but one is a payment invariant and the
other is an admin permission check. Record the distinction in
`ARCHITECTURE.md`. If a mechanical finding exists, `dismiss` it. If you were
about to write a semantic finding, do not.

## How to write the result

If `findings.json` already has an A04 candidate: `coherent review confirm` or
`dismiss` that fingerprint.

Otherwise append to `.coherent/semantic-findings.json`:

- `identity`: `dup-impl:<concept>:<SymbolA>+<SymbolB>`
- `detectionMode`: `hybrid`
- `status`: `confirmed` only when behavior and callers show one authority
- Required Finding fields from [semantic-audits.md](../semantic-audits.md)
