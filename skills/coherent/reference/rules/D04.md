# D04 — Implementation-coupled tests

Investigation procedure only. Catalog metadata lives in
[taxonomy.md](../taxonomy.md). Detection: hybrid. No detector ships yet.
Record in `decisions.json`: review a current audit candidate when present;
otherwise add a semantic finding. Shared write-back: [README.md](README.md).

Do not refactor hundreds of mocks around code that A04–B05 may delete.
Early tests are small safety/characterization tests. Late tests simplify
after production structure stabilizes.

## What to search for

Tests that assert internals, call graphs, or mock interactions instead of
behavior a caller can observe.

- `toHaveBeenCalledWith`, `toHaveBeenCalledTimes`, call-order assertions
- Tests of private methods, unexported helpers, or exact class names
- Snapshots of internal objects that are not a public contract
- Suites that fail when you extract a helper or delete a forwarding hop

Prefer suites that sit next to modules you already touched for A04/B04.

## Distinguish a real issue from an intentional difference

- Intentional: a small characterization test written to protect a cleanup
  (phase 0 / early safety). Name that in `testSafetyEvidence` and leave it.
- Intentional: a contract test against a public API or CLI.
- Real: the suite locks accidental structure; cleanup looks like a mass test
  rewrite, so the structure survives.
- Not D04: a large mock graph (D05) unless the assertions are also
  interaction-based. D05 is how the test is *constructed*; D04 is what it
  *asserts*.

Prefer behavioral tests over implementation-call assertions. That is already
this repo’s testing philosophy.

## Evidence to collect

- Test file, cases, and the production symbols they pin.
- What would break if the hop or helper disappeared.
- Whether a behavioral assertion already exists (or could).
- `deletionOpportunity`: rewrite assertions, not production, unless the
  production hop is itself B04.
- `changeRisk`: losing the only coverage of a critical workflow.

## Successful “do not merge”

A CLI spawn test and a unit test of `buildPlan` look overlapping but one
pins user-visible behavior and the other pins a planner invariant. Keep
both. Do not force everything through one style.

## How to write the result

Review a mechanical finding if present. Otherwise append:

- `identity`: `coupled-test:<test-file>:<case-or-suite>`
- `detectionMode`: `hybrid`
- `status`: `confirmed` when cleanup of a known hop is blocked by
  interaction assertions
