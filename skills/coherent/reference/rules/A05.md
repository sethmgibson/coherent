# A05 — Parallel abstractions

Investigation procedure only. Catalog metadata lives in
[taxonomy.md](../taxonomy.md). Detection: hybrid. No detector ships yet.
Record in `decisions.json`: review a current audit candidate when present;
otherwise add a semantic finding. Shared write-back: [README.md](README.md).

## What to search for

Look for two or more *models of how work is organized*, not two copies of one
function (A04) and not two data types (A06).

Common pairs:

- Service vs use-case vs interactor vs handler
- Repository vs store vs DAO vs gateway
- Client vs gateway vs adapter vs port
- Application vs domain folders that both claim the same use cases

Ask where the last few features landed. If there is no obvious home, agents
will add a third abstraction.

## Distinguish a real issue from an intentional difference

- Intentional: a port/adapter at a real I/O or provider boundary, with one
  policy owner on the inside. Single-implementation ports can still be
  intentional (B03 notes this).
- Intentional: public API vs internal module when architecture names the
  mapping.
- Real: both abstractions are extended; new work cannot tell which to open.
- Not A05: one forwarding wrapper (B04); one interface with one impl and no
  second planned use (B03); two functions that do the same work (A04).

Do not collapse a boundary just because the names overlap.

## Evidence to collect

- Abstraction names → actual responsibilities and callers.
- Landing sites of recent features.
- `authoritativeConcept`: the surviving home for that job.
- `semanticEquivalence`: how the models overlap and where they do not.
- Files that would move or disappear after choosing one home.
- What later cleanup this unlocks (often B04/B05 and A08).

## Successful “do not merge”

`Repository` at the persistence boundary and `Store` as an in-memory cache
are different jobs. Keep both. Write the authority into
`ARCHITECTURE.md` Authoritative representations. Dismiss a mechanical
candidate if one exists.

## How to write the result

Review an existing finding in `decisions.json`, or append a semantic `Finding`:

- `identity`: `parallel-abs:<job>:<NameA>+<NameB>`
- `detectionMode`: `hybrid`
- `status`: `confirmed` when new work has no obvious home; `candidate` when
  the overlap is only structural
