# E01 — Redundant database access

Investigation procedure only. Catalog metadata lives in
[taxonomy.md](../taxonomy.md). Detection: hybrid. Detector emits
`n-plus-one:*` and `repeated-lookup:*`. Shared write-back for explicitly
requested advanced cleanup: [README.md](README.md).
Ordinary reviews follow [data-access.md](../data-access.md) and report in chat
without saved decisions. Optimize paths that remain necessary within scope.

## What to search for

Mechanical: repository/service-style `await` inside a loop; the same lookup
awaited twice in one function.

Also inspect: composed services that each load the same aggregate.
Trace per-item calls in async callbacks, serializers and lazy relations even
when the detector has no signal. Look for database or API reads used only to
obtain a value already derivable from authoritative inputs. The detector does
not establish those semantic cases; inspect their contracts manually.

## Distinguish a real issue from an intentional difference

- Intentional: lookups that must see committed writes between them.
- Intentional: per-item authorization that cannot be batched (rare; prove
  it).
- Real: the shape of the work is known and the same row is loaded N times.
- Real: each of N items loads a different row that one bounded batch could
  retrieve with equivalent access, snapshot and error semantics.
- Real: a balance or status is fetched when complete, correctly scoped inputs
  already determine it under the same freshness and calculation contract.
- Intentional: authoritative read-back, incomplete/paginated inputs, or a read
  with access-validation responsibilities that local arithmetic cannot replace.
- The detector is not proof of operational cost. Confirm scale and that the
  path still exists after design cleanup.

## Evidence to collect

- Function, query/call, loop vs repeated key.
- Data that is actually used (see E03).
- A local load that would be correct.
- For derivation: the exact formula, source completeness, precision and unknown
  handling. For batching: query counts at representative collection sizes and
  equivalent outputs. Parallelizing N calls alone does not remove N+1.
- Check that a batch/join replacement bounds concurrency and does not multiply
  returned rows or distort aggregates. Use E06 for individual query cost and
  workload bounds; fewer queries alone do not establish less database work.

## Successful “do not merge”

Separate order and user reads can serve distinct consumers in one request.
Different keys or stores alone prove neither redundancy nor efficient loading;
trace consumer needs and per-item calls before concluding.

## How to write the result

Report redundant reads, derivable values and N+1 with their contract evidence;
keep uncertain cases as candidates. In explicit advanced cleanup, confirm the
existing finding or add an evidence-backed hybrid finding for a missed case.
Dismiss ordered, write-sensitive lookups only with caller evidence.
