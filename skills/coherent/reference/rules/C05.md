# C05 — Distributed workflow complexity

Investigation procedure only. Catalog metadata lives in
[taxonomy.md](../taxonomy.md). Detection: semantic. Report in chat;
[shared boundaries](README.md) govern optional recording.

Look at this after B01 (which path is living) and C01 (where invariants
live). Do not invent orchestration for a workflow that should collapse.

## What to search for

One business workflow whose complexity is hidden across tightly coupled
helpers or across handlers, queues, crons, retries and sagas without a cohesive
owner. A short parent function can still contain a large implicit workflow.

- ARCHITECTURE.md Critical workflows / Async boundaries that list hops but
  no owner.
- A user action that continues in a queue consumer, then a cron, then
  another handler, with failure handled differently at each hop.
- Replay and idempotency invented per hop.
- New hops added because the existing path is hard to see.
- Helpers called only by one parent that mutate shared state, require the same
  large context, depend on execution order, or communicate through side effects.
- Extracted implementation steps that hide the actual branching and failure
  behavior rather than express independent domain operations.

Trace *one* business outcome end to end. Stop at the hops that outcome
actually uses.

## Distinguish a real issue from an intentional difference

- Intentional: an explicit state machine, saga, or documented orchestrator
  with one owner and known failure/replay rules.
- Intentional: a hard provider boundary (payments, email) called from one
  place.
- Real: the path is accidental; visibility is logs; agents add hops.
- Intentional: small pure helpers with clear inputs and outputs that make the
  parent easier to understand without hidden ordering or state.
- Not C05: pass-through layers without workflow behavior (B01/B04); a handler with
  too many flags (C02/C03).

Synchronous code can hide a distributed workflow across helpers. Absence of
queues does not call for a queue, orchestrator or state machine.

## Evidence to collect

- The business outcome in one sentence.
- Ordered hops: file, symbol, trigger (HTTP, queue, cron).
- For local helper chains: shared reads/writes, ordering constraints, branches
  and errors reconstructed as one workflow, including helpers with one caller.
- Who owns success, failure, and replay today (often: nobody).
- `authoritativeConcept`: the orchestration or the single remaining owner
  after collapse.
- `changeRisk`: replay, double-send, and visibility.
- Existing characterization tests, if any.

Compare a simpler cohesive function, explicit domain operations, and an explicit
state model against the actual complexity. Recommend the smallest meaningful
design; adding orchestration is not the default fix.

## Successful “do not merge”

Two queues that look similar: one is the order workflow, one is an unrelated
outbound email firehose. They stay distinct. Explain both boundaries in chat.

## Advanced recording (explicit opt-in only)

Append to the `findings` array in `.coherent/decisions.json`:

- `identity`: `distributed-wf:<workflow>`
- `detectionMode`: `semantic`
- `status`: `confirmed` when traced coupling obscures state, sequencing or
  failure behavior without a cohesive owner
