# A07 — Stale compatibility

Investigation procedure only. Catalog metadata lives in
[taxonomy.md](../taxonomy.md). Detection: hybrid. Detector emits
`compat:name|branch|comment:...` candidates. Record: `decisions.json`. Shared
write-back: [README.md](README.md).

## What to search for

Mechanical: identifiers (`legacy`, `deprecated`, `compat`, `oldMode`,
`v1`/`v2`), old/new branch conditions, comments about temporary migration.

Then prove whether any caller still needs the old contract: public APIs,
package exports, jobs, CLI flags, persisted documents.

## Distinguish a real issue from an intentional difference

- Intentional: a living dual path with a named consumer and a removal
  condition. Document those three facts; do not delete.
- Real: the old contract has no remaining callers; the shim is now a second
  system.
- Not A07: a fossil layer nobody claims is compatibility (A01); dead code
  with no compat naming (A08).

Do not delete on the naming signal alone. After a confirmed removal, search
for newly dead code, types, tests, helpers, config, and dependencies (A08,
D01).

## Evidence to collect

- The old contract, the new contract, and every remaining caller.
- Removal condition from comments or docs (or the lack of one).
- External/public reachability.
- Tests that still exercise the old path.

## Successful “do not merge”

`oldMode` and `newMode` are both required by an unexpired client. Dismiss
and record consumer + removal condition in Transitional/legacy architecture.

## How to write the result

Confirm in `decisions.json` only after callers are gone. Dismiss if the
consumer is real. Defer if you cannot prove reachability yet.
