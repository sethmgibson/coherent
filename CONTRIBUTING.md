# Contributing to Coherent

Thanks for helping. Coherent is small on purpose, and the most valuable
contributions make it more precise rather than larger: fewer false positives,
clearer playbooks, sharper evidence, and better documentation.

By participating you agree to follow the [Code of Conduct](CODE_OF_CONDUCT.md).

## Ways to contribute

- **Report a wrong finding.** False positives and false negatives are the most
  useful bug reports. Use the *Finding is wrong* issue template and include a
  minimal code sample.
- **Improve a rule playbook.** The playbooks in
  [`skills/coherent/reference/rules/`](skills/coherent/reference/rules/README.md)
  guide agents through each problem class. Concrete examples and clearer
  "intentional distinction" cases help most.
- **Fix a bug or sharpen a detector.** Check open issues first, and open one
  before starting a large change so the approach can be agreed on.
- **Improve the docs.** If something in the README or a reference file doesn't
  match what the CLI actually does, that's a bug.

## Development setup

Requirements:

- Node.js 20 or newer
- [pnpm](https://pnpm.io) (the version is pinned in `package.json`; `corepack enable` picks it up)
- CPython 3.9+ on `PATH` as `python3` or `python`, for the Python analysis tests

```bash
git clone https://github.com/sethmgibson/coherent.git
cd coherent
pnpm install
pnpm build
node dist/cli.js audit tests/fixtures/scanner-app
```

Use pnpm only. Do not commit `package-lock.json` or other lockfiles generated by
a different package manager.

During development you can run the CLI from source without building:

```bash
pnpm exec tsx src/cli.ts audit . --evidence --rules A08
```

## Validation

Run the checks that match your change before opening a pull request:

| Change | Command |
|---|---|
| Any TypeScript change | `pnpm test` and `pnpm typecheck` |
| Rule catalog, phases, or generated skill references | `pnpm check:skill-docs` (`pnpm generate:skill-docs` rewrites them) |
| Finding identity or fingerprints | `pnpm check:unique-fingerprints` |
| CLI surface or package exports | `pnpm build` and `pnpm check:package` |
| Everything CI runs | `pnpm validate` |

CI also runs Coherent on itself (`node dist/cli.js check .` and
`node dist/cli.js doctor . --deep`), so new debt in this repository fails the
build the same way it would in yours.

## Project layout

[`.coherent/ARCHITECTURE.md`](.coherent/ARCHITECTURE.md) is the authoritative
description of ownership and invariants. Read it before changing structure. In
short:

- `src/catalog/rules.ts` and `src/catalog/phases.ts`: the single source of
  truth for rules. `taxonomy.md`, `cleanup-phases.md`, and `runtime.md` under
  `skills/coherent/reference/` are generated from them. Don't edit those by hand.
- `src/detectors/`: one plain function per implemented rule, called explicitly
  from `src/audit/collect.ts`. There is no plugin registry.
- `src/analysis/`: the shared ts-morph project, module resolution, NestJS
  reachability, and the Python sidecar host (`python/analyze.py`).
- `src/review/`, `src/baseline/`, `src/check/`, `src/doctor/`: the optional
  persistent review and CI workflows.
- `src/install/`: Codex and Cursor skill installation and opt-in hooks.
- `skills/coherent/`: the canonical, provider-neutral skill. Files under
  `.agents/` and `.cursor/` are thin discovery adapters, not separate
  methodologies.
- `tests/fixtures/`: small realistic repositories used by the test suite.

## Project invariants

These are the rules most likely to come up in review:

- **Keep proof and judgment separate.** Deterministic findings must be
  mechanically provable. Semantic conclusions need agent or human review, and
  hybrid findings stay candidates until confirmed.
- **Respect write boundaries.** Read-only commands must not create metadata
  unless the user passes an explicit output or integration flag.
- **Never overwrite user content.** Optional integrations must be additive and
  only change content inside Coherent-managed fences.
- **No generic infrastructure.** Don't add plugin hosts, registries, pipelines,
  schedulers, or compatibility shims "for later". Cleanup sequencing belongs
  to the coding agent, not the CLI.
- **Use the canonical terms.** Say *rule*, *finding*, *detection mode*, and
  *cleanup phase*, not "lint", "violation", "diagnostic", or "severity" for
  phases.

## Changing rules and detectors

- **Adding a rule:** add it to `src/catalog/rules.ts`, add its entry to
  `RULE_DETECTOR_REVISIONS` in `src/config.ts`, write its playbook at
  `skills/coherent/reference/rules/<ID>.md`, then run `pnpm generate:skill-docs`.
- **Adding or changing a detector:** keep it a plain function that returns
  evidence. Add a fixture-based test that covers both a true positive and a
  contrasting case that must *not* match. When a detector's output changes,
  bump that rule's entry in `RULE_DETECTOR_REVISIONS` so stale reviews are
  invalidated for that rule only.
- **Changing finding identity:** fingerprints are built from rule ID, identity,
  files, and symbols, never from line numbers. Run
  `pnpm check:unique-fingerprints` and expect review of any change here.

## Testing philosophy

Prefer realistic fixture repositories over mocks. CLI tests spawn the real
command. Catalog tests assert data integrity, not call sequences. Don't add
tests that only prove an internal function was called.

## Pull requests

- Keep each pull request focused on one logical change.
- Write commit messages as a sentence that explains what changed and why, for
  example: "Validate Python sidecar responses and filter rules."
- Fill in the pull request template, including which validation commands you ran.
- Update the README or the relevant reference file when user-facing behavior
  changes, and add an entry under *Unreleased* in [CHANGELOG.md](CHANGELOG.md).
